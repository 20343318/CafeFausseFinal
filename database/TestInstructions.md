# Cafe Fausse database programmer test instructions

This convenience runbook validates DB-05, DB-06, and DB-07 in their approved
order. It is for programmers, is not required by the SRS or rubric, and does
not replace any approved design or verification report.

The workflow is repeatable and restartable. Each run uses a new generated
database named `cafe_fausse_test_harness_<random-id>`. It never reuses a shared
development database.

## Prerequisites

- Run these commands from the repository root in Windows PowerShell 5.1 or
  PowerShell 7.
- PostgreSQL 18.3 must already be running locally on `127.0.0.1`.
- The `pgcrypto` extension must be available.
- Use a PostgreSQL administrator role that can create databases and roles. The
  default examples use `postgres`.
- Do not target production. The harness accepts only `127.0.0.1`, verifies the
  exact port and PostgreSQL version, and creates its own test database.

The person signed in to Windows can run the entire workflow in one terminal.
No separate Windows accounts and no repository password file are needed.

## 1. Run the complete DB-05 through DB-07 gate

If neither `PGPASSWORD` nor `PGPASSFILE` is set, this command securely prompts
once for the PostgreSQL administrator password. Input is not echoed, written to
disk, or printed. The plaintext value exists only in the child PowerShell
process and is removed when that process exits.

```powershell
& .\database\scripts\programmer_test.ps1
```

For a nondefault local port or administrator role, pass them explicitly:

```powershell
& .\database\scripts\programmer_test.ps1 `
    -Port 5433 `
    -AdministratorRole cafe_local_admin
```

If your PostgreSQL client is not on `PATH` or in the standard PostgreSQL 18
installation folder, add:

```powershell
-PsqlPath 'C:\Program Files\PostgreSQL\18\bin\psql.exe'
```

Do not set both `PGPASSWORD` and `PGPASSFILE`. An existing external passfile is
optional; it is never required or generated by this workflow.

Success ends with all of these markers:

```text
[HARNESS:TARGET:PASS]
[HARNESS:OWNERSHIP:PASS]
[HARNESS:DATABASE:PASS]
[HARNESS:ROLES:PASS]
[HARNESS:EXECUTION:PASS]
[HARNESS:CLEANUP-DATABASE:PASS]
[HARNESS:CLEANUP-ROLES:PASS]
[HARNESS:CLEANUP:PASS]
[HARNESS:COMPLETE:PASS]
```

Any failing phase prints `[HARNESS:<area>:FAIL]` and returns a failing
PowerShell error after cleanup has been attempted. PostgreSQL `ERROR` output
from intentional division-by-zero, privilege-denial, timeout, or deadlock tests
is expected only when the enclosing repository test reports `PASS`.

## 2. Repeat the complete gate

Run the same command again. A second successful run proves the normal workflow
does not depend on state left by the first run:

```powershell
& .\database\scripts\programmer_test.ps1
```

## What the complete command runs

The existing `database/scripts/test.ps1` remains the normative automated gate.
The harness invokes it unchanged inside the isolated database, then runs the
final verifier. The order is:

1. DB-05 reset guard, fail-visible SQL, migrations 001-004, behavior tests,
   and runtime privilege denials.
2. Two clean DB-07 rebuilds, which include the DB-06 migrations and seed data.
3. DB-06 behavior, privilege, and 20-iteration concurrency tests.
4. DB-07 behavior, 20-sample performance measurements, and query-plan checks.
5. A final clean rebuild and verification of the approved empty baseline.
6. Harness-owned database, role membership, role, marker, and temporary-file
   cleanup.

No migration, schema rule, allocation behavior, locking behavior, privilege
assertion, iteration count, or performance sample count is weakened.

## 3. Recovery after interruption

Before creating PostgreSQL resources, the harness writes a nonsecret ownership
marker at:

```text
%TEMP%\CafeFausse-db-test-harness\ownership.json
```

On the next invocation, a valid marker is checked against the generated
database name, owner, database comment, role comments, and recorded membership
changes. Only matching resources are removed. The new run then proceeds.

To perform recovery without starting the tests, use the same connection
options as the interrupted run:

```powershell
& .\database\scripts\programmer_test.ps1 -Mode CleanupOnly
```

Malformed, missing, or contradictory ownership evidence causes a fail-safe
refusal. The harness does not guess and does not delete the questionable
resource. Read the failure message before manually investigating. Never delete
the marker first if owned PostgreSQL resources may remain.

## 4. Optional isolated diagnostics

These modes use the same generated database, validation, recovery, and cleanup
rules, but run one checkpoint for investigation:

```powershell
& .\database\scripts\programmer_test.ps1 -Mode DB05
& .\database\scripts\programmer_test.ps1 -Mode DB06
& .\database\scripts\programmer_test.ps1 -Mode DB07
```

They are diagnostics only. They do not replace the complete ordered gate.

## 5. Validate the harness safety behavior

Maintainers can run the controlled safety suite. It injects failures at setup,
database creation, role provisioning, migration, DB-05, DB-06, DB-07, and
pre-final-baseline checkpoints. It also tests simulated interruption recovery,
malformed-marker refusal, ownership-mismatch refusal, preservation of
preexisting resources, exact environment restoration, artifact absence, and
two consecutive complete gates.

```powershell
& .\database\scripts\programmer_test_safety.ps1
```

The safety suite prompts once when no credential source is already configured.
Use `-SkipCompleteRuns` only while developing the harness; it is not sufficient
for release evidence. A full successful safety run ends with:

```text
[HARNESS-TEST:COMPLETE-RUN-1:PASS]
[HARNESS-TEST:COMPLETE-RUN-2:PASS]
[HARNESS-TEST:PREEXISTING-STATE:PASS]
[HARNESS-TEST:GIT-ARTIFACTS:PASS]
[HARNESS-TEST:COMPLETE:PASS]
```

## Resource lifecycle and preservation

The harness may create:

- one generated test database;
- the approved `cafe_fausse_owner`, `cafe_fausse_app`, and
  `cafe_fausse_test` NOLOGIN roles only if they do not already exist;
- direct administrator memberships required by the existing provisioning SQL,
  only if absent before the run;
- the marker and one temporary provisioning wrapper beneath the exact task
  directory above;
- short-lived local `psql` child processes.

Successful or failed cleanup removes only resources proven to belong to the
recorded run. It drops the generated database, revokes only memberships added
by the run, drops only roles created and tagged by the run, terminates only
matching harness database sessions, and removes the exact task directory.

The harness preserves the running PostgreSQL server, the `postgres` maintenance
database, every preexisting database and role, every preexisting role
membership, all caller environment-variable values, the repository files, and
all backend artifacts. It never starts or stops PostgreSQL and never connects
to a production target.
